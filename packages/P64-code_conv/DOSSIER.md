## U1 Digital logic
Give the truth table (or state table) of one part of your circuit and the
simplified Boolean expression you used. Which gates or flip-flops did you need?

### 1. Gray Code Encoding
Gray code is an unweighted unit-distance code where successive values differ in exactly one bit position. For an $n$-bit binary input $B = (b_{n-1}, \dots, b_1, b_0)$ and Gray code output $G = (g_{n-1}, \dots, g_1, g_0)$, each bit is generated by:

$$
g_i = b_i \oplus b_{i+1} \quad (0 \le i < n-1), \qquad g_{n-1} = b_{n-1}
$$

Truth table for a 4-bit slice:

| Decimal | Binary ($b_3 b_2 b_1 b_0$) | Gray Code ($g_3 g_2 g_1 g_0$) | Changed Bit |
| :---: | :---: | :---: | :---: |
| 0 | `0000` | `0000` | — |
| 1 | `0001` | `0001` | $g_0$ |
| 2 | `0010` | `0011` | $g_1$ |
| 3 | `0011` | `0010` | $g_0$ |
| 4 | `0100` | `0110` | $g_2$ |
| 5 | `0101` | `0111` | $g_0$ |
| 6 | `0110` | `0101` | $g_1$ |
| 7 | `0111` | `0100` | $g_0$ |
| 8 | `1000` | `1100` | $g_3$ |
| 9 | `1001` | `1101` | $g_0$ |
| 10 | `1010` | `1111` | $g_1$ |
| 11 | `1011` | `1110` | $g_0$ |
| 12 | `1100` | `1010` | $g_2$ |
| 13 | `1101` | `1011` | $g_0$ |
| 14 | `1110` | `1001` | $g_1$ |
| 15 | `1111` | `1000` | $g_0$ |

Gray decoding (Gray to Binary) cascades XOR gates from MSB down to LSB:

$$
b_{n-1} = g_{n-1}, \qquad b_i = b_{i+1} \oplus g_i \quad (0 \le i < n-1)
$$

### 2. Excess-3 BCD Encoding
Excess-3 is an unweighted self-complementary BCD code formed by adding 3 (`0011`) to each decimal digit ($0 \le d \le 9$). For input bits $A, B, C, D$ (where $A$ is MSB, weight 8, and $D$ is LSB, weight 1):

Truth table for valid BCD digits ($0 \le d \le 9$) and invalid inputs ($10 \le d \le 15$):

| Decimal $d$ | BCD In ($A B C D$) | Excess-3 Out ($E_3 E_2 E_1 E_0$) | Valid Signal |
| :---: | :---: | :---: | :---: |
| 0 | `0000` | `0011` | 1 |
| 1 | `0001` | `0100` | 1 |
| 2 | `0010` | `0101` | 1 |
| 3 | `0011` | `0110` | 1 |
| 4 | `0100` | `0111` | 1 |
| 5 | `0101` | `1000` | 1 |
| 6 | `0110` | `1001` | 1 |
| 7 | `0111` | `1010` | 1 |
| 8 | `1000` | `1011` | 1 |
| 9 | `1001` | `1100` | 1 |
| 10–15 | `1010` – `1111` | `0000` | 0 |

Simplified Boolean expressions derived via Karnaugh maps with validity qualification:

$$
\text{valid} = \overline{A \cdot (B + C)}
$$

$$
E_0 = \overline{D} \cdot \text{valid}
$$

$$
E_1 = \overline{C \oplus D} \cdot \text{valid} = (C \cdot D + \overline{C} \cdot \overline{D}) \cdot \text{valid}
$$

$$
E_2 = (B \oplus (C + D)) \cdot \text{valid}
$$

$$
E_3 = (A + B \cdot (C + D)) \cdot \text{valid}
$$

**Gates Needed:**
- 2-input XOR gates (`XOr`) for Gray encoding/decoding and Excess-3 bit 2/bit 1 calculation.
- 2-input AND (`And`), OR (`Or`), NOT (`Not`), and NAND (`NAnd`) gates for Excess-3 logic and validation masking.
- No flip-flops are used in the combinatorial conversion paths; 16-bit D flip-flops (registers) are only used for the MMIO `VAL` storage register in Verilog.

## U2 Digital components
Which building blocks (adders, multiplexers, decoders, registers, memory)
does your Digital circuit use, and how are they connected?

In [P64.dig](P64.dig), the circuit is built strictly using basic logic gates and structural wiring components without relying on high-level arithmetic blocks or multiplexers:

1. **Splitters and Combiners:**
   - **Input Splitter:** Unpacks the 16-bit input word `val[15:0]` into individual bit signals `v0` through `v15`.
   - **Gray Output Combiner:** Packs the 16 Gray encoded bits `g0` through `g15` into the 16-bit `gray[15:0]` bus.
   - **FromGray Combiner:** Packs the 16 decoded binary bits `b0` through `b15` into the 16-bit `fromgray[15:0]` bus.
   - **Excess-3 Splitter and Combiner:** Decomposes `val[15:0]` into four 4-bit nibbles (`d0` = `val[3:0]`, `d1` = `val[7:4]`, `d2` = `val[11:8]`, `d3` = `val[15:12]`), feeds each into identical 4-bit Excess-3 conversion logic, and combines the four 4-bit outputs into the 16-bit `xs3[15:0]` output bus.

2. **XOR Gate Arrays:**
   - **Gray Encoder:** 15 two-input XOR gates compute $g_i = v_i \oplus v_{i+1}$ for $0 \le i \le 14$, with $g_{15} = v_{15}$.
   - **Gray Decoder:** A 15-gate cascade of two-input XOR gates calculates $b_{15} = v_{15}$, $b_{14} = b_{15} \oplus v_{14}, \dots, b_0 = b_1 \oplus v_0$.

3. **Sub-circuit Logic (Excess-3 Conversion):**
   - Implemented using AND, OR, XOR, and NOT gates evaluating the minimized Boolean equations for each digit in parallel.

4. **Tunnels and Wiring:**
   - Named tunnels clean up routing between input splitters, intermediate logic stages, and output combiners.

## U3 Data representation
Pick three test vectors of your block and explain them in binary, hex and
decimal (signed where it matters). Where could overflow or sign extension go wrong?

### 1. Vector 1: Zero / Minimum unsigned value ($v = 0$)
- **Input:** Decimal `0`, Hex `0x0000`, Binary `0000 0000 0000 0000`.
- **Gray Code:** `0x0000` (`0000 0000 0000 0000`).
- **FromGray:** `0x0000` (Binary `0`).
- **Excess-3:** Each digit is $0$; adding 3 gives $3$ (`0011`$_2$ = `0x3`). The four nibbles produce `0x3333` (Binary `0011 0011 0011 0011`).

### 2. Vector 2: Moderate Value with Multi-digit BCD ($v = 84$)
- **Input:** Decimal `84`, Hex `0x0054`, Binary `0000 0000 0101 0100`.
- **Gray Code:** $84 \oplus (84 \gg 1) = 84 \oplus 42 = 126$ (`0x007E`, Binary `0000 0000 0111 1110`). Notice single-bit transition properties.
- **FromGray:** Decoding `0x0054` as Gray code produces binary `0x0066` (Decimal 102).
- **Excess-3:** Nibble breakdown of `0x0054`: $d_3=0$, $d_2=0$, $d_1=5$, $d_0=4$.
  - $d_3+3 = 3$ (`0011`$_2$)
  - $d_2+3 = 3$ (`0011`$_2$)
  - $d_1+3 = 8$ (`1000`$_2$)
  - $d_0+3 = 7$ (`0111`$_2$)
  - Result: `0x3387` (Binary `0011 0011 1000 0111`).

### 3. Vector 3: Decimal Boundary and Pattern Check ($v = 1234$)
- **Input:** Decimal `1234`, Hex `0x04D2`, Binary `0000 0100 1101 0010`.
- **Gray Code:** $1234 \oplus 617 = 1723$ (`0x06BB`, Binary `0000 0110 1011 1011`).
- **FromGray:** Decoding `0x06BB` restores binary `1234` (`0x04D2`).
- **Excess-3 on Decimal Digits (MMIO peripheral mode):**
  - In the MMIO peripheral module, the input represents decimal 1234 ($d_3=1, d_2=2, d_1=3, d_0=4$).
  - Excess-3 digits: $1+3=4$ (`0100`), $2+3=5$ (`0101`), $3+3=6$ (`0110`), $4+3=7$ (`0111`).
  - Packed XS3 word: `0x00004567`.

### Where Overflow or Sign Extension Could Go Wrong:
- **BCD Nibble Overflow:** In the digital circuit, each 4-bit nibble represents a decimal digit $0 \le d \le 9$. If arbitrary 16-bit hex inputs contain hexadecimal values $10 \le d \le 15$ (`0xA` to `0xF`), standard $+3$ addition would overflow into a 5-bit quantity ($13 \dots 18$), corrupting adjacent nibbles. The design prevents this with explicit validity checking gates that clamp invalid digits to `0`.
- **Sign Extension Bugs:** The input `VAL` is an unsigned 16-bit quantity ($0 \dots 65535$). In RISC-V software, loading halfwords with `LH` sign-extends bit 15 into bits `[31:16]`, turning numbers $\ge 32768$ into negative integers. Programmers must use `LHU` or mask with `0xFFFF` to preserve true 16-bit unsigned representations.
- **Gray Conversion Carry Wrap:** Gray code does not suffer from arithmetic carry overflow because it is a bitwise permutative mapping rather than an arithmetic accumulator.

## U4 Computer organisation
In which step of the instruction cycle (fetch, decode, execute, memory,
write-back, interrupt) does your block do its work? Which instructions need it?

As an MMIO peripheral mapped into Slot 22, P64 operates across the **Execute**, **Memory**, and **Write-Back** steps of the standard instruction cycle:

1. **Execute Stage:**
   - The CPU ALU calculates the effective peripheral register address:
     $$\text{EA} = \text{Reg}[rs1] + \text{offset}$$
     For Slot 22, the base address is `0x0002_0580`.

2. **Memory Stage:**
   - **Write (`SW rs2, offset(rs1)`):** The CPU memory bus controller drives `bus_addr = 0x0002_0580`, `bus_wdata = rs2`, and asserts `bus_we = 1`. P64 latches `wdata[15:0]` into register `VAL` on the rising clock edge.
   - **Combinational Conversion:** As soon as `VAL` is updated, the combinational circuits compute `GRAY`, `FROMGRAY`, and `XS3` in parallel within that same clock cycle.
   - **Read (`LW rd, offset(rs1)`):** The CPU addresses `0x0002_0580` (`VAL`), `0x0002_0584` (`GRAY`), `0x0002_0588` (`FROMGRAY`), `0x0002_058C` (`XS3`), or `0x0002_05BC` (`ID`). P64 decodes `bus_addr[5:2]` and places the requested register value onto `bus_rdata`.

3. **Write-Back Stage:**
   - For `LW`, the CPU write-back multiplexer (`P27`) routes `bus_rdata` to the destination register `rd` in `P13` (`regfile`).

**Instructions Needing It:**
- `SW` (Store Word) to write input operands to `CODECONV_VAL`.
- `LW` (Load Word) to read conversion results from `CODECONV_GRAY`, `CODECONV_FROMGRAY`, and `CODECONV_XS3`.

## U5 Processors
How would a CISC processor, a stack machine or a GPU do the job of your
block differently? (Look at the RISC-V vs Mano comparison in docs/ARCHITECTURE.md.)

- **CISC Processor (e.g., x86):**
  CISC architectures include dedicated microcoded instructions for BCD arithmetic and conversion, such as `DAA` (Decimal Adjust after Addition), `DAS` (Decimal Adjust after Subtraction), `AAA`, and `AAM`. Rather than querying an external MMIO coprocessor via memory instructions, an x86 CPU executes these single-byte instructions in ALU microcode directly on register `AL`. For Gray code, x86 uses fast single-cycle register shift and XOR instructions (`mov ebx, eax; shr ebx, 1; xor eax, ebx`).
- **Stack Machine (e.g., Burroughs B5500, Forth computer, or JVM):**
  A stack machine lacks general-purpose registers. To perform code conversion, it pushes the operand onto the top of the evaluation stack (`PUSH v`), performs a primitive conversion opcode or pops the value to an I/O device controller, and pushes the converted result back onto the stack (`CONV_GRAY`, `POP`).
- **GPU (SIMT Architecture):**
  A GPU executes thousands of threads in parallel. Code conversion is vectorized across SIMD execution lanes using high-throughput bitwise instructions (e.g., CUDA `__byte_perm`, `shfl`, bitwise XOR). Massive parallel lookup tables stored in shared memory or L1 cache are frequently used to convert thousands of BCD or Gray numbers concurrently.
- **Mano's Basic Computer:**
  Mano's 16-bit computer has no native XOR instruction, no BCD adjustment, and no MMIO bus arbitration. Performing Gray encoding requires a software subroutine emulating XOR via Boolean logic:
  $$A \oplus B = (A \land \overline{B}) \lor (\overline{A} \land B)$$
  This takes dozens of cycles of memory loads, complements (`CMA`), additions, and logic AND operations using the single accumulator `AC`.

## U6 Memory and I/O
How does your block take part in a memory access or an I/O transfer? If it
does not, explain which neighbouring block does and how data reaches it.

P64 is a fully integrated Memory-Mapped I/O (MMIO) peripheral occupying **Slot 22** in the RC-V system memory map (`0x0002_0580` – `0x0002_05BF`):

1. **Address Decoding (`P31` - `p31_addr_decoder`):**
   - The CPU issues a memory address on `bus_addr[31:0]`.
   - `P31` decodes bits `bus_addr[15:11]` to detect an I/O space access (`0x0002_0000`) and bits `bus_addr[10:6]` to select the specific peripheral slot. When `bus_addr[10:6] == 22` (`5'b10110`), `P31` asserts `slot_sel[22]` to enable P64.
2. **Register Decoding:**
   - P64 examines `bus_addr[5:2]` (`ridx`) to select the internal register:
     - `ridx 0` (`0x00`): `VAL` (16-bit data register)
     - `ridx 1` (`0x04`): `GRAY` (read-only Gray code of `VAL`)
     - `ridx 2` (`0x08`): `FROMGRAY` (read-only Gray-to-binary decoded value of `VAL`)
     - `ridx 3` (`0x0C`): `XS3` (read-only Excess-3 BCD representation of `VAL`)
     - `ridx 15` (`0x3C`): `ID` (reads constant `32'd64`)
3. **Bus Arbitration and Multiplexing (`P34` & `P33`):**
   - On writes (`bus_we == 1`), `bus_wdata[15:0]` is clocked into `val` when `slot_sel[22]` is high.
   - On reads, P64 outputs its selected 32-bit register value onto its local read bus. `P33` (`p33_rdata_mux`) multiplexes this onto `bus_rdata` based on the active slot grant, which is then returned to the CPU datapath and written into `rd`.

## E1 Instruction trace: SRLI
Trace one **SRLI** instruction through the whole RC-V processor,
block by block (use docs/ARCHITECTURE.md and the simulator's --trace output).

Consider the instruction:
```assembly
srli    t1, t0, 3
```
Assembled instruction at `pc = 0x0000_0238`: `0x0032D313` (`0000000 00011 00101 101 00110 0010011`).
- `opcode` = `0010011` (`0x13`, OP-IMM)
- `rd` = `00110` (`x6` = `t1`)
- `funct3` = `101` (`0x5`, SRLI/SRAI)
- `rs1` = `00101` (`x5` = `t0`, holding `0x0000_0080`)
- `shamt` = `00011` (`3`, immediate bits `[24:20]`)
- `funct7` = `0000000` (`0x00`, logical right shift)

### Simulator Cycle Trace:
```
    53 00000238 0032d313  x6=0x00000010
```

### Detailed Datapath Block Walkthrough:
1. **Instruction Fetch (IF):**
   - **`P04` (`p04_pc_reg`):** Holds current PC `0x0000_0238`.
   - **`P03` (`p03_pc_inc`):** Computes `pc + 4 = 0x0000_023C`.
   - **`P15` (`p15_next_pc`):** Since there is no branch or jump taken, `pcsel` selects `pc + 4` to update `PC` on the next rising clock edge.
   - **`P30` (`p30_rom`):** Fetches 32-bit instruction word `0x0032D313` from address `0x0000_0238`.

2. **Instruction Decode (ID):**
   - **`P17` (`p17_ifields`):** Splits instruction fields: `opcode = 7'h13`, `rd = 5'd6`, `funct3 = 3'b101`, `rs1 = 5'd5`, `rs2 = 5'd3`, `funct7 = 7'h00`.
   - **`P18` (`p18_imm_is`):** Extracts I-type 12-bit immediate `0x003`, sign-extends to 32 bits: `imm_i = 0x0000_0003`.
   - **`P20` (`p20_imm_select`):** Selects `imm_i` (`immsel = 0`), outputting `imm = 0x0000_0003`.
   - **`P21` (`p21_main_dec`):** Sets control signals:
     - `reg_write = 1`
     - `alu_src = 1` (select immediate)
     - `mem_read = 0`, `mem_write = 0`
     - `branch = 0`, `jump = 0`
     - `mem_to_reg = 0` (select ALU result)
   - **`P22` (`p22_alu_dec`):** Decodes `funct3 = 3'b101` and `funct7[5] = 0` into ALU operation `ALU_SRL`.
   - **`P13` (`p13_regfile`):** Reads register `x5` (`rs1`), outputting `rdata1 = 0x0000_0080`.

3. **Execute (EX):**
   - **`P26` (`p26_opab_mux`):** Routes `rdata1` (`0x0000_0080`) to ALU input `opa`, and immediate `imm` (`0x0000_0003`) to ALU input `opb`.
   - **`P01` / `P07` (`p07_alu_shifter`):** Evaluates `opa >> opb[4:0]`:
     $$0x0000\_0080 \gg 3 = 0x0000\_0010 \quad (\text{decimal } 16)$$
     Outputs `alu_result = 0x0000_0010`.
   - **`P09` (`p09_branch_cmp`):** Inactive (no branch evaluation needed).

4. **Memory (MEM):**
   - **`P34` (`p34_bus_arbiter`):** No bus data transaction occurs because `mem_read = 0` and `mem_write = 0`. The memory bus remains idle.

5. **Write-Back (WB):**
   - **`P27` (`p27_wb_mux`):** Routes `alu_result` (`0x0000_0010`) to `wdata`.
   - **`P13` (`p13_regfile`):** With `reg_write = 1`, register `x6` (`t1`) is written with `0x0000_0010` on the rising clock edge.

## E3 Where my block sits
In two or three sentences: which layer of the computer is your block in
(gates / components / datapath / control / instruction set / memory / I/O),
which blocks feed it and which blocks use its output?

P64 resides in the **I/O Peripheral layer** of the RC-V computer as a memory-mapped coprocessor situated on the shared system bus at Slot 22 (`0x0002_0580`). It is fed by the CPU datapath via `P31` (address decoder selecting Slot 22) and `P34` (bus arbiter supplying write data, register offset, and write-enable strobes from store instructions). Its conversion outputs are fed back to `P33` (read-data bus multiplexer), which delivers the converted code words to `P27` (write-back multiplexer) and into the CPU register file (`P13`) during load instructions.
